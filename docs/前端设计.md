这款软件可以先定义成：

> **一个本地优先、键盘优先的文本片段检索与快速粘贴工具。**

它不是传统剪贴板历史，也不是普通笔记软件。用户主动维护一组“键 → 文本内容”，通过全局快捷键呼出窗口，输入 key 或关键词，选中后立即粘贴到当前应用。

类似产品里，Maccy 强调“打开、搜索、回车使用”的键盘优先体验；Espanso 提供全局快捷键呼出搜索栏；Raycast Snippets 则使用名称、Keyword、Tags 和文本内容组织片段。这三种思路正好可以组合成你的产品基础。([Raycast Manual](https://manual.raycast.com/snippets?utm_source=chatgpt.com))

# 一、先确定产品的两个界面

这是整个设计中最关键的决定。

## 1. 快速检索窗口

这是用户每天使用最多的界面：

```text
全局快捷键
  ↓
弹出检索窗口
  ↓
输入 key
  ↓
选择结果
  ↓
粘贴到原来的应用
  ↓
窗口自动关闭
```

它必须：

- 不显示侧边栏
- 不显示复杂导航
- 不要求鼠标操作
- 打开后输入框自动聚焦
- 输入字符后立即筛选
- 回车完成粘贴
- Esc立即关闭
- 完成后恢复到之前的应用

目标是把一次粘贴控制在：

```text
快捷键 → 输入2～5个字符 → 回车
```

------

## 2. 内容管理主窗口

这是低频界面，用于：

- 新建文本
- 编辑文本
- 设置 key
- 添加标签
- 搜索和整理
- 导入导出
- 设置快捷键
- 查看冲突和异常

不要把管理功能塞进快速检索窗口，否则它会逐渐长成一个臃肿的“文本管理后台”。

# 三、先设计核心数据模型

前端开始画页面前，先把一个文本片段定义清楚。

```ts
interface Snippet {
  id: string;

  // 用户输入并用于快速检索的唯一标识
  key: string;

  // 展示名称
  title: string;

  // 实际要粘贴的内容
  content: string;

  // 可选别名
  aliases: string[];

  // 分类标签
  tags: string[];

  // 是否固定在顶部
  pinned: boolean;

  // 使用次数
  usageCount: number;

  // 最近使用时间
  lastUsedAt?: string;

  createdAt: string;
  updatedAt: string;
}
```

示例：

```json
{
  "key": "company-address",
  "title": "公司地址",
  "content": "北京市朝阳区示例路88号A座",
  "aliases": ["addr", "地址", "公司地址"],
  "tags": ["公司", "常用"],
  "pinned": true
}
```

------

## Key规则建议

初版可以采用：

- Key不区分大小写
- Key必须唯一
- 支持字母、数字、`-`、`_`
- 支持前缀匹配
- 支持别名
- 不允许空格
- Key冲突时立即提示
- 删除后进入回收站，而不是直接永久删除

例如：

```text
email-work
email-private
addr-company
reply-delay
reply-thanks
sql-page
api-auth-header
```

不要要求用户记住非常严格的完整 key。建议搜索排序为：

```text
Key完全匹配
→ Key前缀匹配
→ 别名匹配
→ 标题匹配
→ 标签匹配
→ 内容全文匹配
```

这样用户输入 `addr`，可以找到：

```text
addr-company
addr-home
address-en
```

# 四、快速检索窗口怎么设计

## 推荐布局

初版可以采用约 `720 × 460px` 的无边框浮层：

```text
┌──────────────────────────────────────────────────────────┐
│  🔍 输入 Key 或搜索文本…                           ⌘ K  │
├──────────────────────────────────────────────────────────┤
│  ★ addr-company     公司地址                             │
│    email-work       工作邮箱                             │
│    reply-delay      延迟回复说明                         │
│    api-auth         接口认证 Header                      │
│    sql-page         分页查询 SQL                         │
│                                                          │
├──────────────────────────────────────────────────────────┤
│  北京市朝阳区示例路88号A座                               │
│                                                          │
│  ↑↓ 选择    Enter 粘贴    ⌘Enter 复制    Esc 关闭        │
└──────────────────────────────────────────────────────────┘
```

推荐分为四个区域：

### 搜索区

显示：

- 搜索图标
- 当前输入内容
- 清空按钮
- 搜索模式提示

不要在这里放筛选下拉框。快速窗口的每一个额外控件都会拖慢操作。

### 结果区

每条结果只显示：

```text
图标或收藏标记
Key
标题
标签
快捷数字
```

内容不要全部展开，避免结果列表变成大段文字墙。

### 预览区

预览选中片段的实际内容：

- 长文本截断
- 保留换行
- 代码片段使用等宽字体
- 高亮搜索命中内容
- 敏感内容默认遮挡

### 底部快捷键区

只显示当前可用操作：

```text
↑↓ 选择
Enter 粘贴
Ctrl/Cmd + Enter 仅复制
Ctrl/Cmd + E 编辑
Ctrl/Cmd + N 新建
Esc 关闭
```

# 五、核心键盘交互

建议从一开始就写成明确规格。

| 操作               | 行为               |
| ------------------ | ------------------ |
| 全局快捷键         | 打开快速检索窗口   |
| 输入文字           | 实时过滤结果       |
| `↑` / `↓`          | 切换选中项         |
| `Enter`            | 粘贴并关闭         |
| `Ctrl/Cmd + Enter` | 仅复制，不自动粘贴 |
| `Tab`              | 展开或收起预览     |
| `Ctrl/Cmd + E`     | 编辑当前片段       |
| `Ctrl/Cmd + N`     | 创建片段           |
| `Ctrl/Cmd + 1～9`  | 选择对应结果       |
| `Esc`              | 关闭并返回原应用   |

建议把“复制”和“粘贴”设计为两个不同动作：

- **复制**：写入系统剪贴板
- **粘贴**：写入剪贴板后，回到原应用并触发粘贴

这样即使某些应用不允许自动粘贴，用户仍然可以复制后手动粘贴。

```text
└──────────────┴─────────────────────────┴──────────────────────┘
```

## 左侧导航

初版保留：

- 全部片段
- 收藏
- 最近使用
- 标签
- 回收站
- 设置

不要首版就加入文件夹树、多级目录、团队空间。那会把产品从“快捷工具”拖向知识库。

## 中间列表

支持：

- 按更新时间排序
- 按使用频率排序
- 按字母排序
- 搜索
- 多选
- 固定
- 删除
- 拖动排序

## 右侧编辑器

字段顺序建议：

1. Key
2. 名称
3. 内容
4. 别名
5. 标签
6. 行为设置

Key应该放在最上面，因为这是产品最核心的概念。

# 九、推荐的技术与设计产出方式

你本地主要使用 Codex CLI 和 Pi，因此我更推荐：

> **不要把 Figma 当成唯一设计源，先用代码生成可交互的浏览器原型。**

原因很现实：终端 Agent 最擅长读写 Markdown、JSON、HTML、CSS 和 React代码。它们对“根据规格实现一个可运行原型”的控制力，通常比直接操作设计画布更强。

推荐路线：

```text
产品规格 Markdown
→ 低保真 HTML/React 原型
→ 浏览器评审
→ 设计 Tokens
→ 高保真 React 原型
→ Tauri 桌面壳
→ 原生能力接入
```

桌面实现上，`Tauri 2 + React + TypeScript` 很适合这类应用。Tauri目前有官方全局快捷键、剪贴板、系统托盘和开机启动能力，刚好覆盖这款产品的主要桌面集成需求。([Tauri](https://v2.tauri.app/reference/javascript/global-shortcut/?utm_source=chatgpt.com))

但在设计阶段，先不要接入这些原生能力。先模拟：

```text
点击“粘贴”
→ 显示成功提示
→ 关闭模拟弹窗
```

等交互确认后再进入 Tauri 集成。

# 十、Codex CLI 和 Pi 的分工

Codex CLI 是在本地仓库中运行的编码 Agent；Pi则定位为更精简、可扩展的终端编码框架，并支持交互、JSON、RPC和SDK等使用方式。([GitHub](https://github.com/openai/codex/blob/main/README.md?utm_source=chatgpt.com))

你可以这样分工。

## Pi：负责探索和规格

让 Pi承担：

- 需求访谈
- 产品定义
- 用户流程
- 页面规格
- 交互状态
- 竞品思路
- 设计审查
- 发现遗漏

它更像产品经理和UX评审员。

## Codex CLI：负责生成和修改原型

让 Codex负责：

- 初始化前端项目
- 建立组件结构
- 实现页面
- 生成模拟数据
- 修复视觉问题
- 编写交互
- 执行测试
- 根据截图修改页面

它更像前端工程师。

## 不要让两个 Agent 同时随意修改代码

建议：

```text
Pi只允许修改：
docs/
reviews/

Codex允许修改：
src/
tests/
docs/implementation/

共享读取：
AGENTS.md
docs/specs/
docs/ui/
```

这样避免两个 Agent 互相推翻实现。

## 阶段四：人工体验低保真原型

重点不要看“好不好看”，只检查：

- 能不能只用键盘完成核心任务
- 是否能在三步内找到目标文本
- Key相似时是否容易选错
- 长文本是否容易识别
- 预览区域是否必要
- 无结果时下一步是否清楚
- 新建片段是否过于复杂
- 管理窗口是否影响快速窗口

这一步很可能会发现：用户其实更依赖标题和内容搜索，而不是只依赖 key。那就应该在此时调整，而不是写完原生功能再调整。

## 阶段五：让 Pi评审原型

可以把页面截图放进仓库，再让支持图像输入的模型进行评审：

```text
2. 是否存在必须使用鼠标的操作。
3. 是否有规格中未定义的功能。
4. 是否遗漏空状态、错误状态和冲突状态。
5. 搜索结果是否容易区分。
6. 快速窗口是否出现了不必要的管理功能。
7. 是否有可能导致错误粘贴的设计。
8. 是否符合键盘优先原则。

将发现的问题按阻塞、高、中、低四级写入：
docs/reviews/ux-review.md

不要直接修改代码。
```

这里一定要让“生成者”和“评审者”分开。否则 Agent 很容易给自己的作品颁发一个赛博优秀奖。

# 十四、前端设计完成的验收门槛

只有满足以下条件，才算“前端设计出品完成”。

## 产品层

- MVP范围已冻结
- Key规则明确
- 搜索排序明确
- 复制和粘贴行为明确
- 数据默认本地存储

- 快速检索流程可以走通

- 全程可使用键盘
- 无结果有明确处理
- 重复Key有明确提示
- 粘贴失败有降级方案

- 搜索焦点明显

- 浅色和深色模式完整

- 状态矩阵齐全

- 高保真原型可运行

- 所有阻塞问题已关闭

# 十五、最推荐的实际推进顺序

```text
1. 明确MVP和Key规则
2. 完成快速检索窗口UX规格
3. 完成管理窗口UX规格
4. 用Codex生成灰阶React原型
5. 只测试键盘操作和搜索效率
6. 用Pi进行独立UX审查
7. 修正流程
8. 建立Tokens和组件规范
9. 用Codex升级高保真原型
10. 再创建Tauri正式应用
11. 接入全局快捷键、剪贴板和托盘
12. 最后处理自动粘贴与系统权限
```

第一轮设计只需要盯住一个指标：

> 用户能否在不离开键盘的情况下，可靠地找到正确片段并完成粘贴。

只要这个体验成立，这款软件的核心就成立；管理页做得再花哨，也只是勤勤恳恳地给主角搬道具。
